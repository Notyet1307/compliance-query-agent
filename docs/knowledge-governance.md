# 知识来源、版本和质量建设

本文件是建设建议，不是对现行法律或标准的解读。启动包没有打包真实法规标准，不宣称已经查询和验证它们的当前版本。

## 来源分层

| 层 | 建议来源 | 使用方法 |
|---|---|---|
| 原始法律法规/规章 | 正式公布机关的原文、国家法规检索渠道 | 留存正式原文/发布日期/版本/适用边界 |
| 标准 | 标准发布/信息服务渠道及合法授权文本 | 明确版本、生效替代关系和文本使用许可 |
| 政策/行业文件 | 主管部门、监管机构、行业主体的正式文件 | 区分政策、草案、解读和内部工作要求 |
| 企业制度/内部知识 | 组织批准使用的制度与案例 | 单独来源类型与权限，不能冒充普遍法规 |
| 二手解读 | 仅作导航与理解线索 | 不替代被引用的正式依据 |

等保、关基、商用密码的材料分别由相应主题管理员复核；行业知识还要明确行业与地域。以上是拟议责任划分，尚未指定真实负责人。

## 首条真实链路怎么建立

先选一个实际问法和少量必要原文，不先抓取海量 PDF。管理员核对来源、标题、版本、适用日期与原文定位，确认使用/再分发权限，按 corpus 契约整理。原始文件在授权知识系统内保管，仓库只放允许公开的样本或索引；客户材料默认不进公开 Git。

当前程序的本地 JSON 导入仅为受信管理员工作，不向普通用户开放上传/管理接口。知识规模扩展时由 OctoBus 后面的领域知识服务管理，智能体只做有界只读查询。

建议 M1 资料元数据补充：效力层级、适用等级/主体条件、地域/行业层级、废止/替代证据、原始文件 hash、许可/来源获取记录、核验人、nextReviewAt。当前 Source 的最小字段不足以完成自动适用性裁决，不能把这些拟新增字段说成已实现。

## 当前日期语义

`publishedAt`：资料的公布日期；`effectiveFrom/effectiveTo`：记录的有效区间；`validityCheckedAt`：管理员核验时效状态的日期。`generatedAt` 只是本次生成时间，不能取代核验日期。

没有可靠核验记录时，不把抓取时间写成核验通过日期。历史版本不可原地覆盖，重新编写版本与 digest；同一个请求绑定到确定的资料快照。

S1-01 支持以空字符串或省略 `validityCheckedAt` 表示从未完成时效核验，不补抓取日期。相关且在有效区间内的条目进入 `NEEDS_REVIEW`，不调用生成模型；已标未审核／未知状态的条目沿用来源待复核原因，否则返回 `CURRENCY_UNVERIFIED`。非空非法日期或早于公布日的核验日期仍拒绝。`publishedAt` 和 `effectiveFrom` 仍需真实日期；连这些日期也未证实的候选仅保存在审核材料中，不硬凑 corpus。

## 正确答案集

每个样例至少记录问题、范围/日期、应命中的原文与定位、可接受说明、禁止生成的说法、无依据时预期状态。版本迁移、同义词、无依据、跨行业不适用、过期核验、恶意正文分别有例子。

建议先建立 20–30 个经业务人员认可的样例，再判断是否需要分词、混合检索、重排、向量索引。召回率、引用定位正确率、无依据拒答率、版本过滤正确率要分开评测；不能用一个主观“准确率 95%”替代证据。

LLM 能输出 JSON 不代表语义正确。实体、条件、否定词、义务主体和数值都须对照原文检查。当前 `entailmentVerified:false` 应一直保留，直至有独立验收方案，也不能靠另一个模型简单投票改成 true。
